# TDLua 0.6.0

TDLua 0.6.0 adds a host-facing readiness layer, a generic Lua event-loop
driver with optional luv and cqueues adapters, and a multithreaded TDLib
receive/mailbox lifecycle. The existing `receive`, `poll`, `loop`, `on` and
managed Future/Task API keep their v0.5.1 behavior; the new surfaces are
additive.

## Highlights

- **Per-client receive and mailbox lifecycle** on a TDLib worker thread, with
  the Lua API still driven on the owner thread.
- **Owner-wide readiness** exposed through a stable C ABI and a Lua userdata,
  without becoming a second consumer.
- **Generic Lua driver** with bounded turns, per-client slices, stall
  diagnostics and optional reconnection.
- **Optional adapters** for luv and cqueues; neither is a dependency of the
  core module.
- **Multi-client, multi-VM and persistent hosts**, including a custom
  `poll(2)` host through the C ABI.
- **Reconnection through a new generation**, with exactly-once terminal
  notification.

## What is new

### Multithreaded receive and mailbox

Each client has a worker-side receive path and a mailbox. Updates and
responses are delivered to the owner thread by the existing API. Closing a
client, retiring an adapter and detaching an owner are observable and do not
stop unrelated clients.

### Readiness

- Persistent watch demand keeps the TDLib worker reading while no Lua call is
  blocked.
- Readiness is per Lua VM and survives a detached owner as an empty view; it
  never dereferences a dead Lua state.
- A POSIX doorbell (`eventfd`, `socketpair` or pipe) and a Windows `SOCKET`
  doorbell are coalesced notifications; the mailbox is the source of truth.
- The owner-local deadline is the minimum scheduler deadline across the VM's
  clients, with `+inf` when no waiter has a deadline and `0` when one has
  expired.
- `clear()` must be followed by a `has_work()` re-check before parking.

### C ABI

The `tdlua_readiness_*` surface, revision 1, exposes 16 functions with an
opaque `uint64_t` handle, explicit thread rules, status codes and a version
query. The standalone header is installed with the module.

### Lua readiness userdata

`client:readiness([bool | {generic = boolean}])` exposes `fd`, `socket`,
`has_work`, `clear`, `next_deadline`, `reliable`, `valid` and `close`. It adds
no event-loop dependency, no Lua queue and no second mailbox consumer.
`close()` and `__gc` release both interests idempotently; the owner descriptor
is never closed by the handle.

### Generic driver

`tdlua_eventloop.driver` schedules clients in bounded round-robin turns.
`budget` counts `receive` calls; `slice` is a receive-call limit per client,
capped by the remaining budget. The driver reports `sleep`, `again`, `stalled`,
`error` and `closed`, supports a diagnostic or fatal stall, and honours a
bounded `retry_delay`.

### Optional adapters

- `tdlua_eventloop.luv` runs a standalone luv loop or registers on a
  host-owned loop.
- `tdlua_eventloop.cqueues` is the official optional pure-Lua adapter. It
  returns a `pollfd` for an attached or owned cqueues controller, or `nil`
  while the descriptor is not trustworthy. It uses the public TDLua Lua APIs
  and does not require the older C ABI bridge.
- Both adapters disarm an unreliable descriptor, use a bounded 100 ms fallback
  (or a nearer driver deadline), re-arm on recovery, handle a descriptor
  change and surface disarm/re-arm errors as one `on_stop("error", detail)`.
- Terminal notification is exactly-once.

### Error handling and stalls

Supported errors surface through a turn state, a raise, `on_stop`/`on_stall`,
`stats()` or a C ABI status. A non-fatal stall is diagnostic and the loop keeps
running; `stall_fatal = true` makes it terminal.

### Unreliable transport and DEF-01

The v0.6.0 pre-release review found that both official adapters kept polling a
persistently readable EOF descriptor instead of using the bounded fallback.
The defect is fixed in this release: the adapter disarms the unreliable
descriptor, runs the bounded 100 ms fallback (or a nearer deadline), re-arms
when the transport recovers, handles a descriptor change, and reports
disarm/re-arm errors. The R1–R5 regression covers permanent EOF, recovery,
deadlines and kick, lifecycle and host-managed loops.

### Multi-client, multi-VM and reconnection

Multiple clients of one VM are scheduled with a bounded budget. Multiple VMs
use one owner and one driver per owner, with no shared Lua state. A reconnect
is a new generation on a later loop turn; both generations deliver and notify,
and the host loop keeps running.

## Compatibility and migration

- Existing v0.5.1 code using `receive`, `poll`, `loop`, `on`, Futures and Tasks
  is unchanged.
- The new readiness, driver and adapter surfaces are opt-in.
- `tdlua_eventloop` is a separate optional rock; `luv` and `cqueues` are
  optional runtime dependencies of their adapters, never of the core rock.
  `tdlua_eventloop.cqueues` is a pure-Lua adapter. The older C ABI cqueues
  experiment described in `CHANGELOG.md` is a different component and is not a
  prerequisite for this package.
- TDLib is pinned to 1.8.68 (commit `c15d3f5`).
- Lua runtimes: 5.1 (stock, Managed Explicit), 5.2–5.5 (Full Managed), LuaJIT
  2.1 (Full Managed, installed under the Lua 5.1 ABI directory).
- Load `tdlua` on the main thread before creating clients from coroutines;
  first initialization from a coroutine raises.
- **No application migration is claimed.** The release adds opt-in surfaces; it
  does not move existing applications to the new adapters.

## Runtime prerequisites

These requirements describe the **prebuilt binaries**. They are not a promise
of binary portability across all Linux distributions. If your distribution
does not provide the exact shared-library SONAMEs, build from source (see
`LuaRocks and source builds`) instead of renaming or symlinking an ABI library.

### Linux x86_64

- glibc providing symbols up to `GLIBC_2.38`;
- libstdc++ providing `GLIBCXX_3.4.32` and `CXXABI_1.3.13`;
- OpenSSL 3 (`libssl.so.3`, `libcrypto.so.3`) and zlib (`libz.so.1`);
- the Lua shared library for the module you load:

| Module ABI | Required shared library |
|---|---|
| Lua 5.2 | `liblua5.2.so.0` |
| Lua 5.3 | `liblua5.3.so.0` |
| Lua 5.4 | `liblua5.4.so.0` |
| LuaJIT 2.1 | `libluajit-5.1.so.2` |
| Lua 5.5 | no host `liblua` shared library; Lua 5.5.0 is linked statically (see below) |

The Lua 5.5 modules statically link the pinned Lua 5.5.0 runtime. They require
a Lua 5.5.0-compatible host and do not need `liblua5.5.so`. The Lua 5.5.0
license notice is reproduced in `third-party/Lua-5.5.txt` and is shipped as the
`Lua-5.5-LICENSE.txt` release asset. Anyone redistributing the 5.5 modules
must include that notice with the binaries.

TDLib is linked statically on Linux.

### Linux AArch64

The same glibc, libstdc++, OpenSSL 3 and zlib requirements, plus
`liblua5.4.so.0`. Lua 5.4 only.

### Windows x64

- `lua54.dll` from the host;
- the MSVC runtime (`MSVCP140.dll`, `VCRUNTIME140.dll`,
  `VCRUNTIME140_1.dll`, UCRT);
- OpenSSL 3 and zlib are bundled in the archive;
- the JSON archive also ships `tdjson.dll`; the native archive is built with
  MSVC and does not.
- Lua 5.4 only.

### macOS arm64

- Lua 5.4 from the host, with `liblua.5.4.dylib` reachable by the dynamic
  loader;
- OpenSSL 3 from Homebrew under `/opt/homebrew/opt/openssl@3`;
- the module deployment target is macOS 13.0; the dependency set was validated
  on macOS 26 and records a higher dependency floor. Earlier macOS versions and
  lower deployment targets are unverified;
- the JSON archive ships `libtdjson.1.8.68.dylib`; the native archive does not.
- Lua 5.4 only.

### LuaRocks and source builds

- `tdlua` builds from source against the Lua selected by LuaRocks; this is the
  portable path when a prebuilt module's Lua SONAME is unavailable.
- `tdlua-luajit` requires LuaJIT 2.1: point `LUA` at the LuaJIT interpreter.
- Source builds compile the pinned TDLib and take several minutes.
- `TDLUA_BUNDLED_TDLIB=ON` (the default) is the portable source path. The
  `tdlib-static` artifact used by CI is built on Ubuntu and its CMake targets
  refer to Ubuntu multiarch library paths; do not use that artifact as a
  cross-distribution package.

## Known limitations

- **Bounded retention:** 1024 items and a 120 s TTL, drop-oldest, with
  `dropped_overflow`/`dropped_expired` and separate
  `dropped_subscription_*` counters. Overload or a long host suspension can
  lose buffered updates.
- **Fairness is bounded round-robin**, not a latency SLA. A busy client can
  delay a sparse one within the configured budget.
- **Windows SOCKET reconnection is not validated.**
- **macOS and AArch64 host-managed/reconnect are not fully validated.**
- **cqueues runtime is verified on Lua 5.4 only.**
- **cqueues attached two-generation reconnect is not demonstrated.**
- **Authenticated Telegram (Level C) is not executed.** Real auth transitions
  and network-loss reconnection need a separate campaign.
- **LuaSocket is a host-demonstrated integration pattern, not an official
  adapter.** OpenResty, Copas and Lanes remain application integrations.
- **A same-`fd` descriptor change can surface `EEXIST` on luv.** It is reported
  as a terminal `on_stop("error")`, not a silent loop; rebuild the adapter on a
  later turn.
- **`tdlua_readiness_deadline` D3 is sensitive to runner load.**
- **The M2 50-request burst is local evidence**, not a dedicated release
  workflow job.
- **Linux prebuilt Lua SONAMEs:** see the table above. Distributions that do
  not provide the exact SONAME must build from source.
