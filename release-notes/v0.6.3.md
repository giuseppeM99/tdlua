# TDLua 0.6.3

TDLua 0.6.3 adds future composition to `execute`, a synchronous fast path that
avoids submitting requests TDLib can answer immediately, `tdlua.ref` field
projections, and a fix that preserves binding and TDLib error messages on
LuaJIT. It moves the pinned TDLib to 1.8.71. The module version string is
`0.6.3-1.8.71`; `tdlua.tdlib_version` reports `1.8.71`. The readiness C ABI
stays at revision 1.

`execute(request)` now always returns a Future, including when TDLib answers
synchronously. This is an intentional breaking change described under
[Compatibility](#compatibility); use `execute(request):wait()`, or the raw
`execute(request, timeout)`, `execute(request, false)` and `executeSync(request)`
forms, to keep the previous table result.

## Highlights

- **Future composition**: a request may contain whole Futures and
  `tdlua.ref(future, path)` projections. A request whose dependencies are
  already terminal is materialized inline; a request with pending dependencies
  is snapshotted and submitted exactly once when the last dependency becomes
  terminal.
- **Synchronous fast path**: for a request without pending dependencies,
  `execute` first asks TDLib to execute it synchronously. Only the two literal
  TDLib markers authorise an asynchronous retry; any other reply, including a
  real `400`, is the result.
- **`execute(request):wait()`** works on both the synchronous and the
  asynchronous path, and never sends a request twice.
- **LuaJIT error messages**: a foreign unwind from `lua_error()` is no longer
  mistaken for an unknown C++ exception, so binding and TDLib errors keep their
  original text.
- **TDLib 1.8.71**, pinned at commit
  `f10611ee1f03f91ddae8185483a1ccfd3d664668`.
- Completion observers, readiness, the luv/cqueues/Copas adapters and the
  packaging layout from 0.6.2 are preserved.

## What is new

### Future composition

`execute(request)` accepts, in any request position and at any depth up to 100
table levels:

- a whole Future: the resolved value is copied as the request value;
- `tdlua.ref(future, "field")` or `tdlua.ref(future, "a.b.c")`: only the
  projected field is copied.

The request table is traversed with raw reads only: `__index` is never
consulted and no value is converted during the scan. With terminal
dependencies the request is materialized in the calling `execute` and takes the
synchronous fast path. With pending dependencies the request is copied once
into a metatable-free snapshot with private dependency slots; the user table is
never modified, and a Future observed both whole and through a projection is
observed once.

A failed dependency, or a dependency that resolved with a TDLib `error` object,
fails the dependent Future without sending anything. The dependent request's
own TDLib error remains a value. Cycles, a Task used as a value, `__index` in a
composed tree, a dependency owned by another client, and fire-and-forget with
pending dependencies are rejected explicitly.

`tdlua.ref()` pins the projected Future for the lifetime of the composition. A
missing field is an explicit error, not `nil`.

`timeout` remains a total budget from the invocation. A positive budget can
prevent a late submission; `timeout <= 0` keeps the historical "submit and do
not wait" form. There is no dedicated composition timer: a dependency that never
becomes terminal retains the dependent Future until `close()`. This is a
documented limitation, not a hidden poll.

### Synchronous fast path

For a request without pending dependencies the binding asks TDLib to execute it
synchronously before submitting a managed request:

- an object reply makes the Future terminal immediately, with no submission;
- a `400` whose message is exactly
  `The method can't be executed synchronously` or
  `The option can't be get synchronously` authorises the asynchronous path, and
  the request is submitted exactly once;
- any other error, including `Request is empty`, a text parse error or another
  real `400`, is the response; it is never retried;
- a missing synchronous answer is a local error
  (`tdlua: synchronous execution returned no result`) and is never retried,
  because the operation may already have run.

There is no whitelist of synchronous methods and no fallback based on the error
code alone. Task, callback, coroutine and fire-and-forget forms never use the
fast path. The two markers were verified unchanged in TDLib 1.8.71:
`SynchronousRequests.h/.cpp`, `Td.cpp` and `Client.cpp` are byte-identical to
1.8.70.

### `execute` forms and `execute(req):wait()`

| Form | Return |
|---|---|
| `execute(request)` | Future |
| `execute(request, timeout > 0)` | result, or `nil, "timeout"` |
| `execute(request, timeout <= 0)` | result; submit and do not wait for the budget |
| `execute(request, false)` | result; blocking wait without a budget |
| `execute(request, true)` | request id; fire-and-forget |
| `execute(request, callback[, context])` | Task |
| `execute(request, coroutine[, context])` | Task |

`execute(request):wait()` settles a synchronous fast-path result and an
asynchronous result alike, and `Future:wait()` keeps its blocking semantics on
both. The dynamic helpers (`client:getOption{...}`,
`client:getUser{...}` and the other generated methods) follow the same forms.
`executeSync(request)` and `_execute(request)` keep the raw table/request-id
API. Result tables never carry Future methods.

### LuaJIT error messages

LuaJIT raises `lua_error()` with a foreign unwind. The inner binding boundary
converted a C++ error into a Lua error and called `lua_error()`; the unwind then
crossed the outer `protected_call`, whose catch-all replaced the message with
`tdlua: unknown C++ exception`. The outer boundary now rethrows a foreign unwind
when `std::current_exception()` is empty, so LuaJIT unwinds to its own protected
frame and keeps the original error. Exceptions derived from `std::exception`
keep `what()`; only genuinely unknown C++ exceptions use the generic text.

### Completion observers

The 0.6.2 completion surface is unchanged. `Future:on_complete()` and
`Task:on_complete()` return a token and schedule the callback exactly once, on
the owner thread, inside a scheduler tick. The module advertises the surface
through `tdlua.capabilities.on_complete`. A queued completion is work:
`readiness:has_work()` stays true and the registration rings the owner doorbell.
`token:cancel()` returns true only while the callback has not started;
`waiter:cancel()` and `Driver:clear()` keep their 0.6.1 behaviour.
`Bridge.new()` keeps its `completion`, `on_watch`, `timer_module`,
`wake_retry_limit` and `wake_retry_delay` arguments, including the bounded
`retry_delay = 0.01` wake retry and the `wake_fatal` terminal state. The MSVC
`R12` registration split and its `longjmp` ownership rule remain in force. These
phrases are part of the public 0.6.2 contract and are retained in 0.6.3.
`tdlua_eventloop.copas` and `tdlua_eventloop.copas_bridge` keep their names,
arguments and return conventions.

### TDLib 1.8.71

The `td` submodule is pinned to
`f10611ee1f03f91ddae8185483a1ccfd3d664668`, the first upstream commit whose
effective version is 1.8.71 ("Update version to 1.8.71.", 2026-11-22). No
upstream tag `v1.8.71` exists. The three later `master` commits that still
reported 1.8.71 are deliberately excluded.

Compared with 1.8.70 (`23383aef218a3123f02b744bfa91bde21056a814`):

- functions: 1099 → 1114 (+17, −2, 3 changed);
- types: 2307 → 2358 (+51, 0 removed, 11 with changed fields);
- the synchronous-request implementation, `Td.cpp` and `Client.cpp` are
  unchanged;
- `ClientJson.cpp` now normalises an error message that is not valid UTF-8 to
  `Strings must be encoded in UTF-8`;
- CMake adds `AiComposeStyle.cpp/.h/.hpp`, `tdutils/Action.h`, and lets a
  caller override `TD_GIT_COMMIT_HASH` in the cache. No new external dependency
  is introduced.

## Compatibility

### Intentional Lua API change

`execute(request)` and the dynamic helpers now return a Future instead of the
raw TDLib table, including for a synchronous success. Code that indexed the
result directly must either call `:wait()` or use one of the raw forms:

```lua
-- 0.6.3, both paths
local me = client:getMe():wait()

-- raw forms, unchanged
local value = client:execute({_ = "getLogVerbosityLevel"}, 5)
local value = client:execute({_ = "getLogVerbosityLevel"}, false)
local value = client:executeSync({_ = "getLogVerbosityLevel"})
```

`execute(request):wait()` is the compatibility path for both the synchronous
fast path and the asynchronous fallback. The timeout, fire-and-forget, Task and
callback forms keep their previous return conventions.

### TDLib 1.8.71 API changes

TDLua does not wrap the removed TDLib methods, but applications may call them:

- removed: `getUpgradedGiftWithdrawalUrl` and `withdrawUpgradedGift`; use
  `getGiftMintingUrl` and `mintGift`;
- new required arguments: `getForumTopics` gained
  `icon_custom_emoji_id`, `exclude_open` and `exclude_closed`;
  `searchGiftsForResale` gained `for_grams` and `for_fragment`;
- `replyToCallbackQueryWithEphemeralMessage` now returns `Message`, not `Ok`;
- renamed fields: `export_date` → `mint_date` (`messageUpgradedGift`,
  `receivedGift`, `upgradeGiftResult`), `minimum_price` → `min_price`
  (`upgradedGiftValueInfo`), and `text` → `blocks`
  (`pageBlockExpandableBlockQuote`, `inputPageBlockExpandableBlockQuote`).

The TDLib JSON and native bindings are regenerated from the pinned schema, so
the new methods and fields are available automatically. The native backend
still targets the managed runtimes Lua 5.2–5.5 and LuaJIT; stock Lua 5.1 keeps
the JSON/managed-explicit surface.

### Runtimes and ABI

- Lua 5.1 (stock, Managed Explicit), 5.2–5.5 (Full Managed), LuaJIT 2.1
  (Full Managed, installed under the Lua 5.1 ABI directory).
- The readiness C ABI stays at revision 1; the 16 `tdlua_readiness_*` exports
  and `tdlua_readiness_has_work` (mailbox-only) are unchanged.
- Load `tdlua` on the main thread before creating clients from coroutines; a
  first initialization from a coroutine raises.
- **No application migration is claimed.** The release adds opt-in surfaces; it
  does not move existing applications to composition or to another adapter.

## Copas prerequisites

- Copas 4.12.0 or newer and LuaSocket for the Copas adapter and bridge.
- The bridge falls back to polling when the binding does not export
  `tdlua.capabilities.on_complete`; 0.6.3 always exports it.
- The cqueues runtime is verified on Lua 5.4 only; luv and Copas are verified on
  their documented runtimes.
- The adapter is cooperative: it provides readiness and wakeups, not
  preemption. There is no guaranteed or universal CPU bound; a hostile callback
  can still monopolise its turn.
- The `readiness` level is per VM and the managed-adapter retention/polling
  bounds remain the 0.6.1 limits: 1024 retained entries, 120 s maximum
  retention, drop-oldest eviction. These are safety bounds, not delivery
  guarantees.

## Known limitations

### Unreliable transport and DEF-01

- TDLib remains the network owner. A transport failure, a reconnection or a
  `Windows SOCKET reconnection` can delay a response; TDLua does not add a
  second network queue.
- The existing DEF-01 transport and close rules are unchanged. `close()` is the
  terminal boundary; a pending request is settled or failed by teardown, not by
  a hidden retry.
- `macOS and AArch64` use the same managed lifecycle; the platform-specific
  probes cover close, GC and receiver residency.

### Synchronous fast path

- Only the two literal TDLib markers authorise the asynchronous fallback. If a
  future TDLib changes them, TDLua must be updated; 1.8.71 is verified.
- A missing synchronous answer is a local error and is never retried. This is
  deliberate: the operation may already have run.
- The fast path is not used by Task, callback, coroutine or fire-and-forget
  forms.

### Future composition

- There is no dedicated composition timer. A dependency that never becomes
  terminal retains the dependent Future until `close()`; a positive timeout can
  prevent a late submission but does not cancel a pending dependency.
- `timeout <= 0` means "submit and do not wait", not "zero budget".
- Cross-client dependencies are rejected; a composition belongs to one client.
- Fire-and-forget with pending dependencies, a Task used as a value, `__index`
  in a composed tree and cyclic requests are rejected.
- The scan stops at 100 table levels and reports a depth error instead of
  truncating silently.

### Error delivery and adapters

- A Lua error in a completion callback is recorded and raised by the next public
  call that drains the scheduler; it does not unwind the tick.
- A cancelled token releases the host observer, not the TDLib request.
- A terminal result delivered after a waiter was cancelled is observed and
  discarded.
- The adapter's documented cancellation, timeout and teardown rules are
  unchanged from 0.6.2. The readiness wake retry is bounded to 10 ms per
  attempt, and `tdlua_eventloop.luv` and `tdlua_eventloop.cqueues` do not load
  Copas or LuaSocket.
- **Authenticated Telegram (Level C) is not executed.** The matrices use a real
  TDLib worker and the real adapters, but no authorized account session.

### LuaJIT

- Genuinely unknown C++ exceptions still use the generic
  `tdlua: unknown C++ exception` text. Errors derived from `std::exception` and
  Lua/TDLib errors keep their message.
