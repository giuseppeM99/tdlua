# TDLua 0.6.2

TDLua 0.6.2 adds push-based completion observers to the managed API, makes a
pending completion visible to the readiness layer, and fixes a liveness defect
that could leave an event-loop adapter parked while a deferred completion was
waiting. It also aligns the Copas bridge with the new capability, fixes an MSVC
registration-failure path, and moves the LuaRocks specifications into
`rockspecs/`. TDLib stays at 1.8.70 and the readiness C ABI stays at revision 1.

## Highlights

- **Completion observers**: `Future:on_complete()` and `Task:on_complete()`
  register a callback that runs exactly once when the handle becomes terminal,
  without a blocking wait and without a second consumer. The module advertises
  the surface through `tdlua.capabilities.on_complete`.
- **Completion readiness**: a queued completion is *work*. `readiness:has_work()`
  stays true while an observer is queued and the registration rings the owner
  doorbell, so an adapter that was already parked takes a turn and delivers the
  callback without an application `kick()`.
- **Liveness fix**: the readiness level and the owner edge agree again. An
  adapter parked before a deferred completion is registered no longer waits for
  an unrelated update before running the callback.
- **MSVC R12 fix**: the failure path of `on_complete` registration is split so
  the frame that calls `lua_error` owns no C++ state and crosses no EH cleanup
  funclet.
- **Copas bridge**: uses the completion observers when the binding exposes
  `tdlua.capabilities.on_complete`, keeps polling everywhere else, and retries a
  failed wake with a bounded delay.
- **Lua 5.1 JSON module**: the payload now ships eleven Linux x86_64 modules,
  including the Lua 5.1 JSON build. There is no Lua 5.1 native module.
- **Repository layout**: every LuaRocks specification lives in `rockspecs/`.
- No change to the readiness C ABI revision 1, to the luv/cqueues adapters'
  behaviour, or to the TDLib version.

## What is new

### Completion observers

`Future:on_complete(callback)` and `Task:on_complete(callback)` return a token
and schedule the callback on the owner thread, inside a scheduler tick:

- The callback runs exactly once, after the handle is terminal, with the handle
  as its argument. Registration never runs the callback synchronously.
- A registration on an already-terminal handle is *deferred* to a later turn, so
  a callback can never recurse into `on_complete`.
- The callback may read the result with `handle:wait()`; it must not yield and
  must not drive the scheduler (`poll()`, `loop()`, `receive()`, an adapter turn
  or `tick()`). Registering another observer from inside the callback is
  allowed and is delivered on a later tick.
- Dropping the token does not cancel the observer: it stays active until
  delivery, cancellation, client close or teardown. `token:cancel()` returns
  `true` only while the callback has not started.

`tdlua.capabilities.on_complete` reports whether the loaded module exports the
surface. The flag is per module, not per client, and a binding built without the
observers reports `false` while the rest of the API keeps working.

### Completion readiness and adapter liveness

The readiness level now includes managed completion work for every core of the
VM. While an observer is queued, `readiness:has_work()` returns true; when the
registration happens, the owner doorbell is rung so an adapter parked in its
own poll wakes up.

- The delivery stays deferred and non-reentrant, as described above.
- The level state keeps a host from parking while an entry is pending, so the
  host cannot starve a deferred completion by sleeping on a dead descriptor.
- Cancelling a deferred observer leaves no periodic wake and no spin. The next
  turn drains the cancelled entry; until that turn, `has_work()` still reports
  it, which is deliberate: a level-true host must not park before the queue is
  drained.
- The readiness C ABI is unchanged. `tdlua_readiness_has_work` keeps its
  mailbox-only meaning; the managed completion level is part of the Lua
  readiness surface used by the event-loop adapters.
- A stale wake is harmless. The adapter takes one bounded turn, observes no
  work, and parks again; the fix removes the missed wake, it does not add a
  polling loop.

### MSVC R12 registration failure

Registering an observer can fail (scheduler storage unavailable, allocation
failure, Lua error). Under `/EHsc`, MSVC gives a function that has both a
`try`/`catch` and non-trivial automatics an EH cleanup funclet; a Lua `longjmp`
raised from inside such a frame unwinds through `RtlUnwind` and destroys objects
the frame no longer owns (R12).

The registration is therefore two-phase. Phase one owns the scheduler lease, the
observer and the token publication, and releases everything before returning.
Phase two is the only frame that calls a Lua function able to `longjmp`, and it
owns nothing: a trivially destructible result crosses the boundary by value. The
same split is used by the Windows-portable diagnostic probe, so the property is
checked on MSVC and on GCC/Clang.

### Error propagation and tokens

- A Lua error raised by a completion callback does not unwind the scheduler
  tick. It is recorded and raised by the next public call that drains the
  scheduler: `receive`, `poll`, `loop` or an adapter turn.
- An adapter reports a recorded callback error and stops with that error instead
  of silently dropping it. The client stays usable; the error is not swallowed.
- `token:cancel()` is not request cancellation. It releases the host observer;
  the TDLib request stays pending until its response or the client close.
- A token that is dropped, collected or cancelled after delivery has no effect.
  Delivery is exactly once even if the handle is already terminal when the
  observer is registered.
- Closing the client or tearing down the router releases every pending observer
  before the storage is destroyed; a teardown cannot leave a callback pointing
  at a freed core.

### Copas bridge and fallback

`tdlua_eventloop.copas_bridge` now uses `Future:on_complete()` and
`Task:on_complete()` when `tdlua.capabilities.on_complete` is true:

- The observer only signals readiness and wakes the Copas coroutine; the waiter
  coroutine reads the result with `wait()` after `ready()` returned true.
- `Bridge.new()` accepts `completion`, `on_watch`, `timer_module`,
  `wake_retry_limit` and `wake_retry_delay`. `completion = false` forces the
  polling path; a binding without the capability also stays on polling.
- The bridge no longer scans notify waiters in `bridge:poll()`. Polling remains
  for `await_poll()`, for `completion = false` and for bindings without the
  capability.
- A wakeup failure retries with `copas.timer`; after `wake_retry_limit` the
  bridge sets `wake_fatal` and the adapter stops with an error instead of
  spinning.
- A waiter cancelled or timed out on a pending request releases its token and
  handle. A terminal result that arrives later is observed and discarded; a
  later unobserved Task failure follows the existing core policy.
- The adapter chains and restores the bridge `on_watch` hook during teardown.
- `Driver:clear()` and `driver:clear()` keep their 0.6.1 behaviour: they drain
  the owner doorbell without consuming an update and without closing the
  descriptor.
- The 0.6.1 surface is preserved: the driver, `copas`, `copas_socket` and
  `copas_bridge` keep their names, arguments and return conventions. An
  application written for 0.6.1 does not change.

### Packaging and repository layout

- All LuaRocks specifications moved to `rockspecs/`, including the versioned
  event-loop rock. The build and release workflows reference the new paths and
  `tdlua_eventloop-0.6.2-1.rockspec` is the versioned candidate for this
  release. No packaged artifact, dependency or module changed.
- The release payload now includes the Lua 5.1 JSON module: eleven Linux
  x86_64 `.so` modules, twenty-four checksums and twenty-five payload files.
  There is no Lua 5.1 native module, because the native backend targets the
  managed 5.2+ runtimes.
- The rockspec descriptions were refreshed: the LuaJIT rock no longer claims
  the 0.4 managed API, and the core description names the completion observers.

## Compatibility

- Existing 0.6.1 code using `receive`, `poll`, `loop`, `on`, Futures, Tasks, the
  readiness userdata, the luv/cqueues adapters and the Copas adapter/bridge is
  unchanged.
- The readiness C ABI revision 1 and the 16 `tdlua_readiness_*` exports are
  unchanged; `tdlua_readiness_has_work` remains mailbox-only.
- `tdlua_eventloop` stays a separate optional rock with the deliberate
  dependency `tdlua >= 0.6.0`. luv, cqueues, Copas and LuaSocket remain optional
  runtime requirements of their adapters; the core rock has no event-loop
  dependency.
- Lua runtimes: 5.1 (stock, Managed Explicit), 5.2–5.5 (Full Managed), LuaJIT
  2.1 (Full Managed, installed under the Lua 5.1 ABI directory).
- Load `tdlua` on the main thread before creating clients from coroutines;
  first initialization from a coroutine raises.
- **No application migration is claimed.** The release adds opt-in surfaces; it
  does not move existing applications to completion observers or to another
  adapter.

### TDLib 1.8.70

TDLib stays at 1.8.70 (commit `23383aef218a3123f02b744bfa91bde21056a814`).
The module version string is `0.6.2-1.8.70`; `tdlua.tdlib_version` reports
`1.8.70`. TDLib is pinned by the `td` submodule and by the workflows, and a
module built against a different TDLib commit is not a supported combination.
No TDLua API change in this release depends on TDLib.

## Runtime prerequisites

These requirements describe the **prebuilt binaries**. They are not a promise
of binary portability across all Linux distributions. If your distribution
does not provide the exact shared-library SONAMEs, build from source instead of
renaming or symlinking an ABI library.

### Linux x86_64

- glibc providing symbols up to `GLIBC_2.38`;
- libstdc++ providing `GLIBCXX_3.4.32` and `CXXABI_1.3.13`;
- OpenSSL 3 (`libssl.so.3`, `libcrypto.so.3`) and zlib (`libz.so.1`);
- the Lua shared library for the module you load:

| Module ABI | Required shared library |
|---|---|
| Lua 5.2 | `liblua5.2.so.0` |
| Lua 5.3 | `liblua5.3.so.0` |
| Lua 5.4 | `liblua5.4.so.0` |
| LuaJIT 2.1 | `libluajit-5.1.so.2` |
| Lua 5.5 | no host `liblua` shared library; Lua 5.5.0 is linked statically (see below) |

The Lua 5.5 modules statically link the pinned Lua 5.5.0 runtime. They require
a Lua 5.5.0-compatible host and do not need `liblua5.5.so`. The Lua 5.5.0
license notice is reproduced in `third-party/Lua-5.5.txt` and is shipped as the
`Lua-5.5-LICENSE.txt` release asset. Anyone redistributing the 5.5 modules
must include that notice with the binaries.

TDLib is linked statically on Linux.

### Linux AArch64

The same glibc, libstdc++, OpenSSL 3 and zlib requirements, plus
`liblua5.4.so.0`. Lua 5.4 only.

### Windows x64

- `lua54.dll` from the host;
- the MSVC runtime (`MSVCP140.dll`, `VCRUNTIME140.dll`,
  `VCRUNTIME140_1.dll`, UCRT);
- OpenSSL 3 and zlib are bundled in the archive;
- the JSON archive also ships `tdjson.dll`; the native archive is built with
  MSVC and does not;
- Lua 5.4 only. The Copas adapter is not supported on Windows.

### macOS arm64

- Lua 5.4 from the host, with `liblua.5.4.dylib` reachable by the dynamic
  loader;
- OpenSSL 3 from Homebrew under `/opt/homebrew/opt/openssl@3`;
- the module deployment target is macOS 13.0; the dependency set was validated
  on macOS 26 and records a higher dependency floor. Earlier macOS versions and
  lower deployment targets are unverified;
- the JSON archive ships `libtdjson.1.8.70.dylib`; the native archive does not;
- Lua 5.4 only.

### LuaRocks and source builds

- `tdlua` builds from source against the Lua selected by LuaRocks; this is the
  portable path when a prebuilt module's Lua SONAME is unavailable.
- `tdlua-luajit` requires LuaJIT 2.1: point `LUA` at the LuaJIT interpreter.
- `tdlua_eventloop` installs the pure-Lua driver and the optional adapters. It
  requires the `tdlua` core rock but no event-loop runtime; each adapter loads
  its own loop inside `new()`.
- The versioned specifications are in `rockspecs/`; the release workflow
  generates the core and LuaJIT rocks from the `scm-1` files and copies
  `rockspecs/tdlua_eventloop-0.6.2-1.rockspec` unchanged.
- Source builds compile the pinned TDLib and take several minutes.
- `TDLUA_BUNDLED_TDLIB=ON` (the default) is the portable source path.

## Copas prerequisites

- **Copas 4.12.0**, pinned at commit
  `f4dd9fad5b6b65806c090fadc18488f6a7cc3145`.
- **LuaSocket**, installed from the LuaSocket 3.1.0-1 rock, which reports
  `_VERSION` `"LuaSocket 3.0.0"`. Only that runtime was executed.
- POSIX only. Windows is rejected by `Copas.is_supported_platform()`.
- `socket.select` is limited by `FD_SETSIZE` (`1024` here). The proxy turns an
  exceeded set into a terminal error, never a busy loop.
- Upgrading Copas or LuaSocket requires re-running the pinned matrix: the
  adapter relies on the documented `select` duck typing and on
  `copas.receive` accepting a non-socket object.

## Known limitations

- **The completion readiness level is per VM, not per client.** `has_work()`
  reports the union of the managed work of every core in the VM. A driver that
  pumps only one client can therefore see work that belongs to another client of
  the same VM and keep its bounded retry running until that client is drained.
  The current configuration uses `retry_delay = 0.01` s (`10 ms`) for that
  bounded retry. This is a latency and CPU cost, not a correctness failure:
  no guaranteed or universal CPU consumption is claimed, and the host is
  expected to make every relevant client progress. The adapters are not changed
  to work around it; see `tdlua_eventloop/README.md` for the driver-level
  contract.
- **Copas is not supported on Windows.** The constructor rejects it; luv
  remains the Windows adapter.
- **The Copas deterministic suite is not validated on macOS.** It depends on
  fake-TCP timing that is not portable to the macOS runner. macOS runs the
  real-runtime Copas smoke instead, which is the gate for that platform.
- **Copas and LuaSocket are optional.** The core rock has no dependency on
  either, and `tdlua_eventloop.luv`/`tdlua_eventloop.cqueues` do not load them.
- **`Future:wait()` on a pending handle is not interoperable with Copas.**
  Use the bridge; TDLua never resumes a Copas coroutine.
- **Waiter cancellation is not TDLib request cancellation.** `waiter:cancel()`
  releases the host wait only; the request remains pending.
- **Completion observers are delivered by the scheduler, not by a thread.** A
  host that never drains the scheduler (`receive`, `poll`, `loop`, an adapter
  turn or `tick()`) never runs the callback.
- **Bounded retention:** 1024 items and a 120 s TTL, drop-oldest, with
  `dropped_overflow`/`dropped_expired` and separate
  `dropped_subscription_*` counters. Overload or a long host suspension can
  lose buffered updates.
- **Fairness is bounded round-robin**, not a latency SLA.
- **Windows SOCKET reconnection is not validated.**
- **macOS and AArch64 host-managed/reconnect are not fully validated.**
- **cqueues runtime is verified on Lua 5.4 only.**
- **Authenticated Telegram (Level C) is not executed.** The matrices use a real
  TDLib worker and the real adapters, but no authorized account session.
- **LuaSocket is loaded only by the Copas adapter.** It is not a dependency of
  the core or of the luv/cqueues adapters.
- **Linux prebuilt Lua SONAMEs:** see the table above.

### Unreliable transport and DEF-01

The DEF-01 unreliable-transport regression remains the reference for bounded,
lossy and reconnecting transports. It runs 160 checks on the real TDLib worker
and is green locally, in the dry run and on master. The Copas adapter keeps its
bounded `hard_fallback` retry for a broken or unreliable descriptor; it does not
change the DEF-01 semantics, and a fatal stall is reported once through
`on_stop("stalled")` rather than retried forever.

### Completion delivery bounds

- A deferred completion is delivered by the next scheduler turn; there is no
  timer that forces a turn, and no background thread.
- A wake rung for an entry that was cancelled or already drained costs one
  bounded turn. It does not create a permanent wake-up loop.
- A callback error is raised once, by the next public call that drains the
  scheduler. It is not retried.
