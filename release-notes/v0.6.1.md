# TDLua 0.6.1

TDLua 0.6.1 is an additive release on top of 0.6.0. It adds an optional Copas
adapter and a Copas-owned coroutine bridge to `tdlua_eventloop`, adds the
`Driver:clear()` helper, and moves the pinned TDLib to 1.8.70. The core module,
the C ABI, the backends, the managed `Future`/`Task` API and the luv/cqueues
adapters are unchanged.

## Highlights

- **Optional Copas adapter** (`tdlua_eventloop.copas`) that drives one Copas
  coroutine over the existing readiness surface, in standalone or host-managed
  mode, with exactly-once `on_stop` and non-fatal `on_stall` diagnostics.
- **Copas coroutine bridge** (`tdlua_eventloop.copas_bridge`) that lets a Copas
  coroutine await a managed handle without TDLua ever resuming a Copas
  coroutine.
- **`Driver:clear()`**, an additive host primitive that drains the owner
  doorbell without consuming an update and without closing the descriptor.
- **TDLib 1.8.70** (commit `23383aef218a3123f02b744bfa91bde21056a814`),
  updated from 1.8.68.
- No change to the core C++ implementation or to the readiness C ABI revision 1.

## What is new

### Copas adapter

`tdlua_eventloop.copas` is a pure-Lua optional adapter. It loads Copas and
LuaSocket only inside `Copas.new()`, never at require time, and the core
`tdlua` module never loads it.

- `Copas.is_supported_platform()` returns `false` on Windows. `Copas.new()`
  rejects Windows before loading Copas; luv remains the Windows adapter.
- The adapter uses the driver itself as its readiness source (`fd`, `socket`,
  `valid`, `reliable`, `has_work`, `clear`). It never acquires a second
  readiness handle and never closes or duplicates the owner descriptor.
- Standalone mode: `adapter:run()` creates exactly one Copas coroutine and
  drives `copas.step()` until retirement.
- Host-managed mode: `adapter:start()` creates the coroutine without driving it
  and `adapter:step([timeout])` performs one Copas turn, so the host keeps its
  own loop.
- `adapter:kick()`, `adapter:stop()`, `adapter:is_running()`,
  `adapter:is_stopped()` and `adapter:stats()` complete the lifecycle.
- `on_stop(reason, detail, adapter)` runs exactly once, after the proxy is
  detached, the hook restored, the driver stopped and an owned bridge
  destroyed. `on_stall(state, adapter)` fires once per non-fatal episode and is
  contained in `stats().stall_error`.
- `max_park` (default `0.25` s, `math.huge` allowed) and `hard_fallback`
  (default `0.1` s, must be finite) bound one park and the unreliable-descriptor
  retry.

`tdlua_eventloop.copas_socket` is a private, non-application proxy. It
implements the LuaSocket/Copas duck typing used by `select` and
`copas.receive` (`getfd`, `dirty`, `receive`, `settimeout`, `close`).
`close()` is a deliberate no-op: the descriptor belongs to the VM owner.
`getfd()` returns `-1` when the descriptor is closed, invalid or unreliable.

### Coroutine bridge

`tdlua_eventloop.copas_bridge` owns waiters, not requests:

- `bridge:waiter([label])` creates a single-use waiter.
- `waiter:callback()` returns a TDLua callback that completes the waiter
  without yielding, for use inside a managed Task on the owner thread.
- `bridge:poll()` is called by the adapter after every driver turn and
  completes waiters whose handle is already terminal. It never calls `wait()`
  on a pending handle.
- `bridge:await_handle(handle, [timeout], [label])` parks the scheduler
  coroutine until completion, timeout, cancellation or destroy.
- `bridge:await_poll(handle, [timeout], [interval], [label])` is the explicit
  timer-driven variant for hosts without the adapter.
- `waiter:complete(...)`, `waiter:fail(err)`, `waiter:cancel([err])`,
  `waiter:is_done()`, `waiter:wait([timeout])` and `bridge:destroy()` complete
  the surface. Completion is exactly-once, multiple return values and `nil` are
  preserved, and a terminal waiter drops its coroutine reference.

### Driver addition

`tdlua_eventloop.driver` gains one additive method:

- `driver:clear() -> true | false | nil, err` drains the owner doorbell through
  the current primary readiness handle. It does not consume a client update,
  does not close the descriptor, and returns `false` when the driver has no
  live client. Existing adapters are unaffected.

### Ownership rules

- TDLua never resumes a Copas coroutine. The adapter resumes only the coroutine
  it created, and the bridge parks and wakes through Copas.
- One owner thread, one driver and one consumer per client. The adapter is not
  a second consumer; updates are still delivered by `receive`, `poll`, `loop`
  and the managed API.
- A Lua callback that runs inside `driver:tick()` must not yield. The adapter
  protects its own loop body; it cannot protect arbitrary host callbacks.
- Do not call `Future:wait()` or `Task:wait()` on a pending handle from inside
  a Copas coroutine. That is a documented ownership violation, not a supported
  path: TDLua would resume the Copas coroutine it does not own. Use
  `bridge:await_handle()` or the callback returned by `waiter:callback()`.
- Waiter cancellation is not request cancellation. `waiter:cancel()` cancels
  the host wait only; the TDLib request stays pending until its response or the
  client close. No request-id cancellation is exposed.

## Compatibility

- Existing 0.6.0 code using `receive`, `poll`, `loop`, `on`, Futures, Tasks and
  the readiness userdata is unchanged.
- The core C++ implementation, the readiness C ABI revision 1 and the 16
  `tdlua_readiness_*` exports are unchanged.
- `tdlua_eventloop.luv` and `tdlua_eventloop.cqueues` are unchanged.
- `tdlua_eventloop` stays a separate optional rock. luv, cqueues, Copas and
  LuaSocket are optional runtime requirements of their adapters; the core rock
  has no event-loop dependency.
- Lua runtimes: 5.1 (stock, Managed Explicit), 5.2–5.5 (Full Managed), LuaJIT
  2.1 (Full Managed, installed under the Lua 5.1 ABI directory).
- Load `tdlua` on the main thread before creating clients from coroutines;
  first initialization from a coroutine raises.
- **No application migration is claimed.** The release adds opt-in surfaces; it
  does not move existing applications to Copas or to any other adapter.

### TDLib 1.8.70

TDLib moves from 1.8.68 to 1.8.70. The module version string is
`0.6.1-1.8.70`; `tdlua.tdlib_version` reports `1.8.70`. TDLib is pinned by the
`td` submodule and by the workflows, and a module built against a different
TDLib commit is not a supported combination. No TDLua API change depends on the
TDLib bump.

## Runtime prerequisites

These requirements describe the **prebuilt binaries**. They are not a promise
of binary portability across all Linux distributions. If your distribution
does not provide the exact shared-library SONAMEs, build from source instead of
renaming or symlinking an ABI library.

### Linux x86_64

- glibc providing symbols up to `GLIBC_2.38`;
- libstdc++ providing `GLIBCXX_3.4.32` and `CXXABI_1.3.13`;
- OpenSSL 3 (`libssl.so.3`, `libcrypto.so.3`) and zlib (`libz.so.1`);
- the Lua shared library for the module you load:

| Module ABI | Required shared library |
|---|---|
| Lua 5.2 | `liblua5.2.so.0` |
| Lua 5.3 | `liblua5.3.so.0` |
| Lua 5.4 | `liblua5.4.so.0` |
| LuaJIT 2.1 | `libluajit-5.1.so.2` |
| Lua 5.5 | no host `liblua` shared library; Lua 5.5.0 is linked statically (see below) |

The Lua 5.5 modules statically link the pinned Lua 5.5.0 runtime. They require
a Lua 5.5.0-compatible host and do not need `liblua5.5.so`. The Lua 5.5.0
license notice is reproduced in `third-party/Lua-5.5.txt` and is shipped as the
`Lua-5.5-LICENSE.txt` release asset. Anyone redistributing the 5.5 modules
must include that notice with the binaries.

TDLib is linked statically on Linux.

### Linux AArch64

The same glibc, libstdc++, OpenSSL 3 and zlib requirements, plus
`liblua5.4.so.0`. Lua 5.4 only.

### Windows x64

- `lua54.dll` from the host;
- the MSVC runtime (`MSVCP140.dll`, `VCRUNTIME140.dll`,
  `VCRUNTIME140_1.dll`, UCRT);
- OpenSSL 3 and zlib are bundled in the archive;
- the JSON archive also ships `tdjson.dll`; the native archive is built with
  MSVC and does not;
- Lua 5.4 only. The Copas adapter is not supported on Windows.

### macOS arm64

- Lua 5.4 from the host, with `liblua.5.4.dylib` reachable by the dynamic
  loader;
- OpenSSL 3 from Homebrew under `/opt/homebrew/opt/openssl@3`;
- the module deployment target is macOS 13.0; the dependency set was validated
  on macOS 26 and records a higher dependency floor. Earlier macOS versions and
  lower deployment targets are unverified;
- the JSON archive ships `libtdjson.1.8.70.dylib`; the native archive does not;
- Lua 5.4 only.

### LuaRocks and source builds

- `tdlua` builds from source against the Lua selected by LuaRocks; this is the
  portable path when a prebuilt module's Lua SONAME is unavailable.
- `tdlua-luajit` requires LuaJIT 2.1: point `LUA` at the LuaJIT interpreter.
- `tdlua_eventloop` installs the pure-Lua driver and the optional adapters. It
  requires the `tdlua` core rock but no event-loop runtime; each adapter loads
  its own loop inside `new()`.
- Source builds compile the pinned TDLib and take several minutes.
- `TDLUA_BUNDLED_TDLIB=ON` (the default) is the portable source path.

## Copas prerequisites

- **Copas 4.12.0**, pinned at commit
  `f4dd9fad5b6b65806c090fadc18488f6a7cc3145`.
- **LuaSocket**, installed from the LuaSocket 3.1.0-1 rock, which reports
  `_VERSION` `"LuaSocket 3.0.0"`. Only that runtime was executed.
- POSIX only. Windows is rejected by `Copas.is_supported_platform()`.
- `socket.select` is limited by `FD_SETSIZE` (`1024` here). The proxy turns an
  exceeded set into a terminal error, never a busy loop.
- Upgrading Copas or LuaSocket requires re-running the pinned matrix: the
  adapter relies on the documented `select` duck typing and on
  `copas.receive` accepting a non-socket object.

## Known limitations

- **Copas is not supported on Windows.** The constructor rejects it; luv
  remains the Windows adapter.
- **The Copas deterministic suite is not validated on macOS.** It depends on
  fake-TCP timing that is not portable to the macOS runner. macOS runs the
  real-runtime Copas smoke instead, which is the gate for that platform.
- **Copas and LuaSocket are optional.** The core rock has no dependency on
  either, and `tdlua_eventloop.luv`/`tdlua_eventloop.cqueues` do not load them.
- **`Future:wait()` on a pending handle is not interoperable with Copas.**
  Use the bridge; see Ownership rules above.
- **Waiter cancellation is not TDLib request cancellation.** Cancelling a
  waiter releases the host wait only; the request remains pending.
- **P2 completion observation is not implemented.** There is no general
  push-based observation of an arbitrary pending managed handle beyond the
  callback-Task path and the adapter-polled `ready()` path.
- **Bounded retention:** 1024 items and a 120 s TTL, drop-oldest, with
  `dropped_overflow`/`dropped_expired` and separate
  `dropped_subscription_*` counters. Overload or a long host suspension can
  lose buffered updates.
- **Fairness is bounded round-robin**, not a latency SLA.
- **Windows SOCKET reconnection is not validated.**
- **macOS and AArch64 host-managed/reconnect are not fully validated.**
- **cqueues runtime is verified on Lua 5.4 only.**
- **Authenticated Telegram (Level C) is not executed.** The Copas matrix uses a
  real TDLib worker and real Copas, but no authorized account session.
- **LuaSocket is loaded only by the Copas adapter.** It is not a dependency of
  the core or of the luv/cqueues adapters.
- **Linux prebuilt Lua SONAMEs:** see the table above.

### Unreliable transport and DEF-01

The DEF-01 unreliable-transport regression remains the reference for bounded,
lossy and reconnecting transports. It runs 160 checks on the real TDLib worker
and is green locally, in the dry run and on master. The Copas adapter adds a
bounded `hard_fallback` retry for a broken or unreliable descriptor; it does
not change the DEF-01 semantics, and a fatal stall is reported once through
`on_stop("stalled")` rather than retried forever.
